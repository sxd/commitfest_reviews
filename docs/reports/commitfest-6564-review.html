Reject ADD CONSTRAINT NOT NULL if name mismatches existing domain not-null constraint

Target: CommitFest patch 6564 Head: 2fb8da5a245661287833b05a1b2e275ddf83bbd7 Verdict: needs-review Blocker counts: verified=0, unverified=0 Model: glm-5.2:cloud Date: 2026-08-30

Patch summary

The patch extends the table-column name-mismatch check (commit 96e2af60504) to domain NOT NULL constraints in AlterDomainAddConstraint (src/backend/commands/typecmds.c). When ALTER DOMAIN ... ADD CONSTRAINT <name> NOT NULL is issued on a domain already marked typnotnull and the supplied name differs from the existing NOT NULL constraint's name, it now throws ERRCODE_OBJECT_NOT_IN_PREREQUISITE_STATE instead of silently accepting the redundant add. Unnamed adds and same-name adds remain idempotent (no-op success), matching ALTER DOMAIN ... SET NOT NULL / ALTER DOMAIN ... ADD NOT NULL semantics and the table-column behavior.

Changed files: src/backend/commands/typecmds.c (+25 lines), src/test/regress/expected/domain.out (+11/-1), src/test/regress/sql/domain.sql (+6/-1).

Mechanism: findDomainNotNullConstraint (src/backend/catalog/pg_constraint.c:661-698) returns only validated NOT NULL constraints. Failure: A user-reachable concurrent DDL scenario produces an internal-style elog(ERROR) without an SQLSTATE, degrading the user experience compared to a proper ereport. The elog is used for a condition that is not a true can't-happen invariant violation.
