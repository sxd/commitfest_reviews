CommitFest 6482 Review — CREATE TABLE LIKE INCLUDING COMMENTS copies table-level comment

Patch summary

CREATE TABLE ... LIKE ... INCLUDING COMMENTS previously copied comments on columns, check constraints, not-null constraints, indexes, and extended statistics, but not the comment on the source relation itself. This patch adds that copy.

Changed files (repo-relative):

  • src/backend/parser/parse_utilcmd.c — implementation
  • src/test/regress/expected/create_table_like.out — regression test expected
  • src/test/regress/sql/create_table_like.sql — regression test SQL

Changed symbols: transformTableLikeClause, expandTableLikeClause

What the patch does:

  1. Adds CREATE_TABLE_LIKE_COMMENTS to the deferral-option mask in transformTableLikeClause (parse_utilcmd.c:1311-1317) so expandTableLikeClause is driven when INCLUDING COMMENTS is requested.
  2. Adds a new block in expandTableLikeClause (parse_utilcmd.c:1631-1652) that calls GetComment(RelationGetRelid(relation), RelationRelationId, 0) on the LIKE source and, if non-NULL, builds a CommentStmt with objtype = OBJECT_TABLE and object = list_make2(schemaname, relname) (or list_make1(relname)), appended to result.
  3. Adds a regression test: COMMENT ON TABLE ctlt3 + SELECT obj_description('ctlt13_like'::regclass, 'pg_class').

Provenance / model routes

All seats used model glm-5.2:cloud (user-fixed override). Route policy: user-fixed-model.

Findings

F1

(MAJOR, correctness, verified) — Foreign-table target wrong-object-type

Location: src/backend/parser/parse_utilcmd.c:1642

Mechanism: The new table-comment block hard-codes stmt->objtype = OBJECT_TABLE regardless of the child relation's relkind. When the child is RELKIND_FOREIGN_TABLE (CREATE FOREIGN TABLE ... LIKE ... INCLUDING COMMENTS|ALL), CommentObject → get_object_address → get_relation_by_qualified_relation (objectaddress.c:1472-1478) errors with ERRCODE_WRONG_OBJECT_TYPE and the foreign table is never created. The existing index-copy block is guarded by childrel->rd_rel->relkind != RELKIND_FOREIGN_TABLE (line 1554); the new block has no such guard. This is a functional regression: CREATE FOREIGN TABLE x (LIKE <commented-src> INCLUDING ALL) SERVER s fails where it previously succeeded.

Failure: CREATE FOREIGN TABLE ft (LIKE src INCLUDING COMMENTS) SERVER s errors with ERROR: "ft" is not a table when src carries a table-level comment; the foreign table is not created.

Verification: Reproduced against a staged-build temp instance (CREATE FOREIGN TABLE cf6482_ft (LIKE cf6482_src INCLUDING COMMENTS) SERVER dummy_srv → ERROR: "cf6482_ft" is not a table). Post-fix, the foreign table is created and ft_comment = 'source table comment'.

Repair: Replace stmt->objtype = OBJECT_TABLE; with stmt->objtype = get_relkind_objtype(childrel->rd_rel->relkind);. get_relkind_objtype is already used in this file (line 1166); childrel is in scope. This returns OBJECT_FOREIGN_TABLE for foreign tables and OBJECT_TABLE for plain/partitioned tables, preserving the feature for all relkinds.

Repair validation: Passed — apply-check, diff-check, compile (exit 0), repro (foreign-table target succeeds), targeted-test (cf6482_like_comments + create_table_like both pass via check-tests).

Suggested code (exact postimage):

c
CommentStmt *stmt = makeNode(CommentStmt);
stmt->objtype = get_relkind_objtype(childrel->rd_rel->relkind);
if (heapRel->schemaname)
    stmt->object = (Node *) list_make2(makeString(heapRel->schemaname),
                                      makeString(heapRel->relname));
else
    stmt->object = (Node *) list_make1(makeString(heapRel->relname));

F3

(MINOR, correctness, cannot-verify — design decision pending) — Multi-LIKE last-wins

Location: src/backend/parser/parse_utilcmd.c:1650

Mechanism: With multiple LIKE ... INCLUDING COMMENTS sources each carrying a table comment, CreateComments (comment.c:203-217) replaces the pg_description tuple for (child_oid, RelationRelationId, 0), so the last-applied comment wins silently. The thread intends newline-separated concatenation (Jim Jones 2026-02-13, Carlos 2026-03-24); ZizhuanLiu (2026-07-18) proposed skip-on-multiple. The staged diff implements neither — it silently does last-wins.

Verification: cannot-verify — the behavior is empirically real (reproduced: multi_comment = 'second source comment', reversed = 'source table comment'), but classifying it as a defect requires a design decision pending on the review thread. A typed design-choice safety waiver is applied to the code/patch/validation.

Test example: cf6482_like_comments pins the current last-wins behavior (multi_comment_last_wins = 'second source comment'); must be updated to the chosen contract once decided.
