Findings

F1

— BLOCKER / correctness — collation-distinguish estimation regression

  • Location: src/backend/optimizer/path/equivclass.c:2676-2687 (unconditional strip in exprs_known_equal), manifesting in src/backend/utils/adt/selfuncs.c:3708 (add_unique_group_var).
  • Mechanism: exprs_known_equal unconditionally strips every RelabelType from em->em_expr before equal(). canonicalize_ec_expression (~equivclass.c:517-595) deliberately adds RelabelType to force each EC member's exposed collation to match the EC collation, so collation-differing source expressions are not equal() to the underlying Var. Stripping them makes exprs_known_equal wrongly return true for two Vars equal only under a different collation.
  • Failure: Wrong ndistinct estimate (regression vs master) for add_unique_group_var. For GROUP BY t1.c, t2.c with t1.c (text) and t2.c (domain d_txt_ci collate case_insensitive), the estimate collapses from 144 to 12.
  • Verification status: verified (method: repro). Reproduced live on PostgreSQL 20devel (UTF8+ICU) across three binaries: master → 144 (correct); v1 staged → 12 (REGRESSION); v3 patched → 144 (restored). The partitionwise-join caller (relnode.c:2442) is independently guarded by partcoll1 == exprcoll1 (relnode.c:2453); only the estimation caller is exposed.
  • Thread: already-raised (jian 2026-01-15 + 2026-02-25 demonstrated; author agreed v3 fixes it 2026-02-25).
  • Repair: Replace the unconditional strip with strip_collation_neutral_relabels(), applied symmetrically to item1, item2, and em->em_expr. The helper strips only RelabelType layers whose resultcollid == exprCollation(arg) (collation-neutral), stopping at the first collation-changing layer.
  • Patch: unified diff bound to HEAD 2866d8c7..., sha256 91efdb172de34f5c5d87f95df1ab9e2f756d9f116489a8661344338be34df9d0.
  • Test: new src/test/regress/sql/collate.icu.utf8.sql block asserting est_rows = 144 (fails on v1 with 12).
F2

— MAJOR / correctness — caller/item strip asymmetry

  • Location: src/backend/optimizer/path/equivclass.c:2676-2687.
  • Mechanism: Only EC members (em->em_expr) are stripped, not caller-supplied item1/item2. Two different equality notions depending on which side is wrapped. Latent for current callers (relnode.c passes bare partexprs; selfuncs.c passes bare Vars) but fragile for future callers.
  • Verification status: verified (static analysis of both callers).
  • Repair: strip both sides symmetrically with the same collation-guarded helper (resolves F2 and also F1 for the add_unique_group_var path).
F3

— MAJOR / tests — test does not cover the collation-distinguish regression

  • Location: contrib/postgres_fdw/sql/postgres_fdw.sql:3696-3741.
  • Mechanism: The staged test only exercises the positive partitionwise-join case (default collation varchar hash). It does not assert the negative/estimation behavior; a revert to unconditional strip would pass the suite.
  • Verification status: verified. Confirmed empirically that a naive non-partitioned collation test does NOT distinguish v1 from v3; the regression only manifests in the partitionwise-join path where EC members for partition keys carry the collation-changing RelabelType.
  • Repair: new core collate.icu.utf8 regression test mirroring the thread repro, asserting est_rows = 144.
F4

— NIT / maintainability — NULL-guard stylistic consistency

  • Location: src/backend/optimizer/path/equivclass.c:2679.
  • while (IsA(expr, RelabelType)) omits the expr && NULL guard used by the three sibling loops (lines 924, 950, 2762). Functionally safe (IsA(NULL, RelabelType) is false) but inconsistent. verified. Repair: the helper uses while (expr && IsA(expr, RelabelType)).
F5

— NIT / maintainability — comment/header documentation

  • Location: src/backend/optimizer/path/equivclass.c:2678.
  • The terse comment does not explain the collation guard rationale or reference canonicalize_ec_expression. verified. Repair: expanded comment documenting the collation-neutral strip.

Residual risk

If the staged v1 is committed without the collation guard, GROUP BY/DISTINCT cardinality estimates regress for any case where two EC members share an EC but differ in exposed collation via a domain COLLATE on an ICU nondeterministic collation. This is a planner estimate regression (no wrong results, no crash, no corruption), but it can produce noticeably worse plans. The repair restores master behavior while preserving the intended varchar partitionwise-join benefit.
