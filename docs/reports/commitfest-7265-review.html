Patch Summary

The patch optimizes logical decoding snapshot building. When a committed transaction has catalog changes in a different database than the slot's database, and those changes do not touch shared catalogs, the snapshot is not rebuilt and invalidations are not distributed. A new function InvalidationsTouchSharedCatalog() checks whether invalidation messages in the commit record concern shared catalogs by examining SHAREDINVALSMGR_ID messages (checking rlocator.dbOid == InvalidOid) and all other message types (checking cc.dbId == InvalidOid, since the dbId field is at the same union offset for all non-SMGR types).

Motivation: A single logical slot on db1 is unaffected by ANALYZE/catalog traffic in db2 that pins xmin via a long-running transaction, eliminating O(k²) reorder-buffer spill growth. The reproducer shows 19MB→0 spill reduction.

Findings

F1

— BLOCKER (correctness) — src/backend/replication/logical/decode.c:712

Status: verified (benign)

Mechanism: distribute is computed from InvalidationsTouchSharedCatalog(parsed->nmsgs, parsed->msgs) — the commit record's transactional invalidation messages. But the actual distribution in SnapBuildDistributeSnapshotAndInval uses ReorderBufferGetInvalidations(builder->reorder, xid, &msgs), which returns invalidations accumulated in the reorder buffer from every XLOG_XACT_INVALIDATIONS record. These two sets can diverge when a subtransaction that touched a shared catalog is rolled back via ROLLBACK TO SAVEPOINT: AtEOSubXact_Inval(isCommit=false) discards those messages without propagating them to the parent, so they are absent from parsed->msgs but present in the grow-only reorder buffer.

Impact: The missed invalidations are from a rolled-back subtransaction, so no shared catalog row actually changed — not distributing them is benign. The patch correctly uses parsed->msgs (the commit record) as the decision basis: it contains exactly the invalidations of changes that actually committed. However, the author must document this design rationale and respond to the on-list review.

Thread status: Raised by Shlok Kyal (2026-09-03), author has not replied as of 2026-09-05.

Repair: Comment-only patch (repair_only.patch, SHA-256 032f11395a3dc4cdd046eab9888c90cf16692ad58506a8d51b7f5598bc32e855) documenting why parsed->msgs is the correct basis. Validation: passed (build + all test suites).

Residual Risk

  • The parsed->msgs vs ReorderBufferGetInvalidations divergence (F1) is benign in the current code but could become a real bug if invalidation/rollback handling changes in the future. The documentation repair mitigates this risk.
  • The NULL-guard branch (snapbuild.c:1088 branch 2) is uncovered by the current test set; it requires a cross-DB race during slot initialization or an injection point to exercise deterministically.
  • The SMGR branch in InvalidationsTouchSharedCatalog is dead defensive code; future changes to sinval.h that add new message types with different layouts could break the union overlay assumption.
