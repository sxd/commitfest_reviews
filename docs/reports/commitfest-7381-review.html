The patch adds a new <sect2 id="linux-memory-cgroups"> titled "Linux Control Group Memory Limits" to doc/src/sgml/runtime.sgml, placed between the existing linux-memory-overcommit section and the linux-huge-pages section. It documents:

  • cgroup v2 memory.max limits
  • OOM killer behavior within a cgroup
  • postmaster crash-restart behavior when a backend is OOM-killed
  • which PostgreSQL memory (shared buffers, per-session work_mem, etc.) counts towards the cgroup limit
  • huge pages caveat (not counted towards cgroup usage by default)
  • cross-references to 8 existing GUC/section anchors (all verified to resolve)

Detailed Findings

F1

— MINOR (docs): cgroup v1 dismissal too terse

  • Location: doc/src/sgml/runtime.sgml:1462-1463
  • Mechanism: Text says "Version 1 uses different files and is not covered here" but does not name the v1 equivalent (memory.limit_in_bytes). Some production deployments still run cgroup v1.
  • Failure: A reader on a v1 system may find this section via the index but be unable to map the advice to their system without external research.
  • Verification: verified — kernel cgroup-v2 doc explicitly references "the original memory.limit_in_bytes" as the v1 hard-limit file.
  • Repair: Extend the parenthetical to name memory.limit_in_bytes:
sgml
<filename>memory.max</filename> file.  (Version 1 uses different files
and is not covered here; in version 1 the equivalent file is
<filename>memory.limit_in_bytes</filename>.)
  • Test example: cd doc/src/sgml && make html && grep -q 'memory.limit_in_bytes' postgresql.html (oracle: exit 0)
F2

— MINOR (docs): OOM victim selection nuance omitted

  • Location: doc/src/sgml/runtime.sgml:1466-1468
  • Mechanism: Text says "the OOM killer terminates a process of the cgroup." Kernel docs describe memory.oom.group (kills all tasks together when set) and note the OOM killer may select the postmaster itself as victim.
  • Failure: The phrasing "terminates a process" (singular) does not alert the operator that the postmaster itself could be the OOM victim, or that memory.oom.group would kill all PostgreSQL processes simultaneously.
  • Verification: verified — kernel memory.oom.group doc: "If set, all tasks belonging to the cgroup or to its descendants are killed together or not at all."
  • Repair: Add memory.oom.group parenthetical and postmaster-victim sentence:
sgml
the OOM killer terminates a process of the cgroup (or, if the cgroup has
<filename>memory.oom.group</filename> set, all processes in the cgroup).
The OOM victim could be the postmaster itself.
  • Test example: cd doc/src/sgml && make html && grep -q 'memory.oom.group' postgresql.html && grep -q 'postmaster itself' postgresql.html
F3

— MINOR (docs): Sizing guidance omits temp buffers and other per-process memory

  • Location: doc/src/sgml/runtime.sgml:1476-1487
  • Mechanism: The paragraph enumerates shared_buffers, work_mem, hash_mem_multiplier, maintenance_work_mem, and max_connections but omits temp_buffers, WAL buffers, autovacuum worker memory, parallel worker memory, catalog cache, etc.
  • Failure: An operator following this guidance literally might underestimate actual cgroup memory usage and still hit OOM.
  • Verification: verified — guc-temp-buffers anchor exists in config.sgml (line 1935); WAL buffers, autovacuum workers, parallel workers are all real per-process consumers not mentioned.
  • Repair: Add a non-exhaustive caveat with temp_buffers example:
sgml
total stays below the limit.  Note that this list is not exhaustive;
other per-process memory such as <xref linkend="guc-temp-buffers"/>,
WAL buffers, and catalog caches also counts towards the cgroup usage.
  • Test example: cd doc/src/sgml && make html && grep -q 'not exhaustive' postgresql.html
F4

— NIT (docs): Huge pages caveat could mention memory_hugetlb_accounting

  • Location: doc/src/sgml/runtime.sgml:1485-1487
  • Mechanism: Text says huge pages are "by default not counted" but doesn't name the memory_hugetlb_accounting mount option that changes this, or that it results in SIGBUS rather than OOM kill.
  • Failure: An operator whose system has memory_hugetlb_accounting enabled would get SIGBUS rather than OOM kill and would not be warned.
  • Verification: verified — kernel doc: "Failure to charge a HugeTLB folio to the memory controller results in SIGBUS."
  • Repair: Extend the caveat to name the mount option and SIGBUS:
sgml
(see <xref linkend="guc-huge-pages"/>) is by default not counted towards
the memory usage of the cgroup, unless the cgroup v2 mount option
<option>memory_hugetlb_accounting</option> is used; with that option, a
charge failure results in <systemitem>SIGBUS</systemitem> rather than
an OOM kill.
  • Test example: cd doc/src/sgml && make html && grep -q 'memory_hugetlb_accounting' postgresql.html && grep -q 'SIGBUS' postgresql.html
F5

— NIT (docs/style): Indexterm entries could use <see> cross-reference

  • Location: doc/src/sgml/runtime.sgml:1444-1450
  • Mechanism: "cgroup" and "control group" are near-synonyms; a <see> cross-reference between them would improve index usability. The codebase already uses this pattern for TSC and GEQO.
  • Failure: The index will have two separate entries for essentially the same concept without a cross-reference.
  • Verification: verified — config.sgml has <primary>Time-Stamp Counter</primary><see>TSC</see> and <primary>GEQO</primary><see>genetic query optimization</see>.
  • Repair: Add <see>control group</see> to the cgroup indexterm:
sgml
<indexterm>
 <primary>cgroup</primary>
 <see>control group</see>
</indexterm>
  • Test example: cd doc/src/sgml && make html && grep -qi 'cgroup.*see.*control group' postgresql.html
