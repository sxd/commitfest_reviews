Patch summary

The patch adds a single vacuum_delay_point(false) call at the top of the outer while-loop in gistvacuum_delete_empty_pages(), before ReadBufferExtended and before any buffer lock is acquired. This matches the established convention in the same file:

  • gistvacuumscan() line 248: vacuum_delay_point(false) before read_stream_next_buffer
  • gistvacuumpage() line 492: vacuum_delay_point(false) before ReadBufferExtended in the tail-recursion loop

The function gistvacuum_delete_empty_pages() (introduced by commit 7df159a620b, 2019) is the only GiST vacuum loop that lacked this call. The bool is_analyze parameter was added by e5b0b0ce150 (PG 18+); false is correct for a VACUUM path.

Zero findings. Both the patch-reviewer and security-reviewer seats found no blockers, no changes-requested, no majors, no minors, and no nits.

Patch-reviewer seat

  • Consistency: Verified — vacuum_delay_point(false) is the established throttle point across all index AMs (btvacuumscan, btvacuumpage, ginbulkdelete, ginvacuumcleanup, ginVacuumPostingTreeLeaves, hashbucketcleanup, spgvacuumscan, spgprocesspending, blbulkdelete, blvacuumcleanup, lazy_scan_heap, lazy_vacuum_heap_rel). All use the same pre-buffer-lock placement.
  • Placement correctness: Verified — the call is at the outer-loop top, before ReadBufferExtended at line 530, while no buffer lock is held. The inner leaf-deletion loop correctly does *not* call the delay point (it holds leafbuf exclusively).
  • Argument correctness: Verified — false is correct for a VACUUM path (not ANALYZE). Routes delay timing to PROGRESS_VACUUM_DELAY_TIME.
  • Semantics: Verified — vacuum_delay_point does CHECK_FOR_INTERRUPTS, cost-based delay sleep, config reload, and parallel vacuum balance updates. All four are desirable in this long-running pass.
  • Memory-context filter: No memory-context findings apply. No allocation, no context switching, no catalog access.
