Rationale

Two verified MAJOR findings require author attention before commit:

  • F1 — no regression test exercises the NOT(srckey = destkey) self-loop dedup filter via the UNION ALL path. The proposed TG1 test fills this gap and passed a two-run gate.
  • F2 — generate_undirected_edge_union_query hand-builds a Query/SetOperationStmt tree bypassing transformSetOperationStmt, relying on untested pull_up_simple_union_all invariants. EXPLAIN confirms pull-up fires currently; the proposed TG3 EXPLAIN test guards the plan shape.

One cannot-verify MAJOR is a live, unresolved design objection for the committer:

  • F3 — reviewer Ashutosh Bapat (2026-07-30, thread 651853) argues OR-expansion belongs in the planner, not an unconditional rewriter rewrite ("we should not always rewrite the undirected edge as UNION as the patch does"). The author has not obtained agreement. This is an architectural decision; a committer must weigh it.

Four verified MINOR robustness/style fixes (F4 Assert→elog, F5 operator-validity Assert, F6 composite-key swap Assert, F7 redundant perminfoindex=0) are quick consistency improvements.

Findings

F1

[MAJOR, tests] — No test exercises the self-loop dedup filter via the UNION ALL path

  • Location: src/test/regress/sql/graph_table.sql:536-537
  • Mechanism: test-coverage-gap
  • Description: The new build_edge_self_loop_filter() (NOT(srckey = destkey) on the backward branch) is only invoked when use_union_all = true (distinct path factors, EDGE_PATTERN_ANY, same vertex table). Existing tests hit use_union_all on g4/ptne but contain no self-loop edge (src = dest); the only self-loop edge in the suite (e3_3 at line 399) is exercised via the same-path-factor case which skips UNION ALL. A regression that doubled or dropped self-loops would not be caught.
  • Verification: verified (two-run gate). Patched EXPLAIN shows Filter: (src_id <> dest_id) in the backward branch; self-loop v33|e331|v33 appears once; 77 rows match baseline.
  • Repair: Add TG1 test (INSERT non-self-loop edge, run undirected (a)-[c]-(b) query, EXPLAIN confirming pull-up). Patch sha256 a1f1474e311e22396e3accffbb0803055e2fafdd5a81ecd042ae0855e384f53b, bound to HEAD 7cb9060dcde. Validation: passed (apply-check + compile + targeted-test + two-run).
F2

[MAJOR, correctness] — Hand-built Query/SetOperationStmt bypasses transformSetOperationStmt

  • Location: src/backend/rewrite/rewriteGraphTable.c:630-797
  • Mechanism: architecture-risk
  • Description: generate_undirected_edge_union_query constructs the UNION ALL Query by hand rather than via transformSetOperationStmt. The resulting structure must satisfy every invariant is_simple_union_all/pull_up_simple_union_all expect. A silent pull-up failure would regress performance with no warning. The author's v2 thread post shows pull-up succeeding, but no regression test asserts the plan shape.
  • Verification: verified (EXPLAIN plan shape). Pull-up fires: e3_3 appears as Seq Scan + Subquery Scan with Filter (not an opaque SubqueryScan). The code-quality concern (fragile invariants) remains; TG3 EXPLAIN test guards it.
  • Repair: Add TG3 EXPLAIN test (included in the F1 patch). Patch sha256 a1f1474e311e22396e3accffbb0803055e2fafdd5a81ecd042ae0855e384f53b. Validation: passed (apply-check + compile + targeted-test).
F3

[MAJOR, design] — Unconditional rewrite vs. cost-based OR expansion (live objection)

  • Location: src/backend/rewrite/rewriteGraphTable.c:479-486
  • Mechanism: design-objection
  • Description: The patch unconditionally emits UNION ALL. On-list, Ashutosh Bapat (2026-07-30): "we should not always rewrite the undirected edge as UNION as the patch does" — suggesting cost-based OR-expansion in the planner. The author argues the graph case is special; no agreement reached.
  • Verification: cannot-verify (design decision for committer). Thread ledger confirms the objection is live and unresolved.
  • Repair: waived (design-choice). A code patch cannot resolve a design disagreement. Evidence needed: committer judgment on whether the unconditional rewrite is acceptable or whether cost-based OR-expansion in the planner is required.
F4

[MINOR, robustness] — Assert vs elog for array-size checks

  • Location: src/backend/rewrite/rewriteGraphTable.c:671,677
  • Mechanism: error-handling
  • Description: Assert(n1 == n3) and Assert(n1 == n2) instead of elog(ERROR, ...) as in sibling build_edge_vertex_link_quals:1478-1481. Assert is compiled out in non-cassert builds; catalog corruption would cause silent buffer overrun.
  • Verification: verified (inspection). Sibling function uses elog(ERROR).
  • Repair: Replace Asserts with if (n1 != n3) elog(ERROR, ...) / if (n1 != n2) elog(ERROR, ...). Patch sha256 68817457e0ff7a92af488edeeb20481390e961c6775d4c20e6587310cec54824. Validation: passed (compile + regression identical).

Security review

No exploitable security defects found. The patch preserves the current-user SELECT-privilege model (security_invoker-by-default) for property graph edge relations, including through the new UNION ALL subquery: inner edge-relation RTEs carry RTEPermissionInfo with selectedCols marked; the outer RTE_SUBQUERY correctly skips redundant perminfo. No SQL injection, no privilege escalation, no search_path issue, no TOCTOU, no superuser-guard gap. The one MINOR (Assert-only array checks, F4) is a discipline issue with no SQL-reachable exploit path.

Verified clean / non-findings

  • Memory context: allocations via palloc/makeVar/makeNode in the per-query context; no wrong-context growth.
  • table_open/table_close balance: table_open at 654, table_close(rel, NoLock) at 781; balanced; NoLock correct.
  • SysCache balance: SearchSysCache1(PROPGRAPHELOID) at 656 released at 686; SearchSysCache1(OPEROID) at 826 released at 847; balanced.
  • Permission handling: outer path_query var-pull loop correctly skips RTE_SUBQUERY vars (606-607); inner perminfos handle SELECT privilege.
  • No catalog/storage format change; no OID, catversion, WAL, or pg_dump impact. No docs change required (performance optimization, user-visible semantics unchanged).

Residual risk

  • F3 (design objection) is unresolved on-list; a committer must decide whether the unconditional rewrite is acceptable or whether cost-based OR-expansion in the planner is preferred.
  • F2's hand-built Query relies on pull_up_simple_union_all invariants that are not documented as a contract; a future planner change could silently break the rewrite. The TG3 EXPLAIN test guards against silent regression.
  • Small-scale / cold-cache regression: the unconditional rewrite (F3) could regress cases where the OR/BitmapOr plan is cheaper. The author should present a no-regression benchmark at small scale.
