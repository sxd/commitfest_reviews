CommitFest 6728 Review: md: measure just FileSync() for pgstat_io without FileClose()

Summary

Patch: Reorder FileClose() to execute after pgstat_count_io_op_time() in mdsyncfiletag() (src/backend/storage/smgr/md.c), so that pg_stat_io fsync timing reflects only FileSync() duration and excludes close()/FileClose() overhead.

Author: Jakub Wartak (EnterpriseDB) Verdict: ready-for-committer Findings: 0 (verified clean) Blockers: 0 verified / 0 unverified

The patch is a minimal, correct, low-risk reordering of two adjacent statements in a single function. It does not change error handling, control flow, errno preservation, or resource lifetime — it only changes which operations are included in the fsync IO-time metric reported to pg_stat_io.

Correctness Analysis

errno preservation (unchanged)

save_errno is captured immediately after FileSync() at line 1938 in both orderings. errno = save_errno at line 1946 restores the FileSync errno regardless of whether pgstat_count_io_op_time() or FileClose() runs first. Neither pgstat_count_io_op_time() nor FileClose() can corrupt the saved errno because it is captured before both. The reorder is errno-safe.

IO timing accuracy (the intent)

Before: pgstat_count_io_op_time() measured FileSync() + FileClose() elapsed time (since io_start was set before FileSync). After: pgstat_count_io_op_time() measures only FileSync() elapsed time.

This is the desired behavior: pg_stat_io.fsync_time should reflect only the actual fsync syscall duration, not file-descriptor teardown. FileClose() may invoke pgaio_closing_fd(), close(), and VFD bookkeeping whose cost is unrelated to fsync and would inflate the metric.

Resource lifetime (unchanged)

FileClose() is still called exactly once when need_to_close is true. The file descriptor is still released before mdsyncfiletag returns. No leak or double-close is introduced.

Control flow (unchanged)

No new branches, loops, or early returns are added. The if (need_to_close) guard and return result path are structurally identical; only statement order within the tail block changes.

Security Analysis

No security-relevant changes. The patch does not touch authentication, authorization, privilege checks, search paths, catalog writes, crypto, TLS, or any SQL-reachable input parsing. No new memory-safety risk: FileClose() and pgstat_count_io_op_time() are existing well-audited functions; their argument sets are unchanged. No SECURITY DEFINER or search_path exposure.
