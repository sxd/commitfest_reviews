The patch makes the LSN reported for pg_logical_emit_message() (the message_lsn exposed to output plugins and the logical replication protocol) equal to the start LSN of the LogicalMessage WAL record (buf->origptr), instead of the end LSN (buf->endptr). All other decoded DML records already use origptr. The change aligns the implementation with both the surrounding code and the existing documentation.

Findings

F-001

(MAJOR, tests) — Test coverage regression

Location: src/test/subscription/t/020_messages.pl:97-99,110

Mechanism: The v2 patch removes the lsn = '$message_lsn' filter from the WHERE clause (line 110) but keeps the $message_lsn variable assignment (lines 97-99) dead/unused. The only remaining assertion for the non-transactional message is is($result, qq(77|0), ...) which checks byte values only — no LSN assertion. The test would pass even if the buf->endptr→buf->origptr fix were reverted, so it does not guard against regression of this specific bug. Yugo Nagata explicitly requested the dead variable cleanup on 2026-06-09; v2 did not address it.

Verification: verified — inspection + reproduction (two-run TAP gate). The patched test (v2) does NOT catch the bug; reverting decode.c to endptr would still pass this test.

Critical correction: The test-author's original premise (asserting LSN equality between pg_logical_emit_message() return and the slot's lsn column) was empirically proven wrong. pg_logical_emit_message() returns XLogInsert() = EndRecPtr (the record end), not origptr (the start). On base code, both the slot and the function return endptr — they match. The fix makes the slot report origptr (start), so the correct oracle is slot_lsn < pg_logical_emit_message()_return, not equality.

Repair packet:

  • Instruction: Capture pg_logical_emit_message() return into $txn_message_lsn (transactional) and $message_lsn (non-transactional). Add (lsn < '$..._lsn'::pg_lsn)::text to the SELECT columns. Assert true|1|pgoutput (transactional) and true|77|0 (non-transactional). Remove the dead lsn = '$message_lsn' AND filter; keep WHERE xid = 0. Both variables are now LIVE.
  • Code example (exact-postimage):

``perl is($result, qq(true|77|0), 'non-transactional message slot LSN is the record start (less than pg_logical_emit_message() return); message is M, flag is non-transactional'); ``

  • Patch (HEAD-bound, unified-diff): sha256 683e7d4b1787e2833eea14a206add2a20f62c737ddc587928dd7f3e13c84b9d0, applies to HEAD 7cb9060dcde08ca63df1f0d701b0674e0e8ae811.
  • Repair validation: passed — two-run TAP gate:
  • Run A (base/endptr + test v3): FAILED 2/5 subtests. Transactional got false|1|pgoutput, expected true|1|pgoutput. Non-transactional got false|77|0, expected true|77|0. Byte checks pass; only LSN wrong — catches the bug.
  • Run B (fixed/origptr + test v3): PASSED 5/5 subtests. Two-run gate satisfied: fail-on-old, pass-on-new.

NIT-001

(NIT, release-process) — Back-patch / release-note consideration

Location: doc/src/sgml/release-19.sgml (release notes)

Mechanism: The LSN change is observable to consumers. On the base code, the slot's lsn column for a logical message equals EndRecPtr (end of record). After the fix, it equals ReadRecPtr (start of record). A consumer (e.g. Debezium) comparing pre-fix to post-fix LSNs for the same WAL record would see a different (smaller) value. The original bug report explicitly mentions the Debezium data-loss issue. The thread (message 5f78375e8107feba80374921cfd87633, 2026-07-15) discusses back-patch options.

Verification: verified — inspection.

Repair: No code change. Add a release note when backpatching: "The LSN reported for logical decoding messages (pg_logical_emit_message) is now the WAL record start LSN, consistent with other decoded change types. Previously it was the record end LSN." All repair fields waived (required-external-resource) — this is a release-note process step, not a code defect.
