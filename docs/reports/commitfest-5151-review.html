CF61 Patch 5151 Review — DirtySnapshot Reproducer

Target: CommitFest 61, Patch 5151 — "DirtySnapshot index scan skips concurrently updated tuples leading to lost updates/deletes in logical replication" Author: Michail Nikolaev (michail.nikolaev@gmail.com) Thread: 586062 ([BUG?] check_exclusion_or_unique_constraint false negative) + 621826 (dedicated follow-up) Canonical Message-ID: CANtu0oiktqQ2pwExoXqDpByXNCJa-KE5vQRodTRnmFHN_+qwHg@mail.gmail.com HEAD: 7cb9060dcde08ca63df1f0d701b0674e0e8ae811 Diff SHA: 8a384b61622e7a8e6e5ce4bce35e493343199d410cc151637f3f1e606ce22bb6 Scope identity: diff-8a384b61@HEAD-7cb9060dcde

Patch summary

This is a reproducer patch, not a fix. The author posted it 2024-07-14 to demonstrate a DirtySnapshot false-negative in btree unique index scans during concurrent UPSERT. The patch has two changes:

  1. src/backend/executor/execIndexing.c (+5 lines at L943-947): A hardcoded if (!conflict && values[0] == 31337) { ereport(ERROR, ...) } block inserted after index_endscan(index_scan) in check_exclusion_or_unique_constraint.
  2. src/test/modules/test_misc/t/006_concurrently_unique_fail.pl (new, 39 lines): A pgbench-based reproducer that preloads value 31337 and hammers ON CONFLICT DO UPDATE.

The underlying bug (DirtySnapshot btree scan skipping TIDs on concurrent update) is real and confirmed by Hou zj (FUJITSU) and Andres Freund. The fix is still under development in the dedicated thread 621826 (v10, page-lock retention approach). This CF 5151 reproducer was the *initial* post; the author moved to injection-point-based tests in v2 (2024-08-12).

Verdict

waiting-on-author — 2 verified BLOCKER findings require substantive rework. The patch is a reproducer that the author has already superseded (v2-v10, injection points, page-lock retention fix) in the same thread. It must not be committed to master as-is.

Findings

F-001

BLOCKER — Production-path debug ereport with hardcoded magic value

  • Location: src/backend/executor/execIndexing.c:943-947
  • Class: correctness (also security: user-triggerable DoS, CWE-754)
  • Mechanism: if (!conflict && values[0] == 31337) { ereport(ERROR, (errcode(ERRCODE_EXCLUSION_VIOLATION), errmsg("we know 31337 in the index!"))); } runs on every successful exclusion-constraint check where the first index column Datum equals 31337. Not guarded by #ifdef, GUC, or injection point.
  • Failure: Any legitimate table with value 31337 in the first index column of an exclusion constraint receives ERROR: we know 31337 in the index! during INSERT.
  • Verification: verified by reproduction. Built scope tree, executed INSERT INTO excl_31337 VALUES(31337) → ERROR: we know 31337 in the index! Coverage: line 943 executed 972 times, line 944 (ereport) executed 2 times.
  • Repair: Remove the 5-line block entirely. The existing INJECTION_POINT("check-exclusion-or-unique-constraint-no-conflict", NULL) at L958-960 already provides the correct test-only hook.
  • Repair validation: Patch applied, built, ereport gone (INSERT succeeds), all 245 regress tests pass.
  • Thread: Author already moved to injection points in v2 (thread 586062, 2024-08-12).
