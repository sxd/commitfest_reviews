Summary

The patch adds a static helper llvm_try_inline_function_call() to the LLVM JIT expression compiler that manually inlines a small allowlist of strict, leakproof, two-argument comparison operators (int4eq, int8eq, date_lt, date_gt, date_le, date_ge) by emitting a direct LLVMBuildICmp instead of the generic BuildV1Call out-call. The inlining is gated on fcinfo->flinfo->fn_addr pointer equality and is only reached after the strict-argument NULL-check block (b_nonull). The author reports a 3–5% improvement on 1M dateeq calls.

The patch compiles cleanly with gcc + LLVM 21 (the referenced C functions are declared via the generated src/include/utils/fmgrprotos.h, included transitively through utils/builtins.h). The inlined IR semantics are correct for the current allowlist: int4/DateADT are int32 byval (truncation i64→i32 recovers the int32; signed LLVMIntSLT/SGT/SLE/SGE match the C comparisons, including the date infinity sentinels at INT32_MIN/MAX), int8 is int64 byval (full-width LLVMIntEQ), and resnull=false is correct on the strict path where args are guaranteed non-null.

The concerns are: (F1) the inlined path drops the fcinfo->isnull = false invariant that both BuildV1Call and the interpreter maintain; (F2) the matcher does not validate the strictness/leakproof/byval/nargs properties that make inlining legal, with no guard against drift; and (F3) the new path has no test coverage.

Findings

F1

— MAJOR — correctness — src/backend/jit/llvm/llvmjit_expr.c:79-167

fcinfo->isnull is never reset to false on the inlined path.

The inlined path bypasses BuildV1Call, which emits an IR store of 0 into FunctionCallInfoData.isnull (FIELDNO_FUNCTIONCALLINFODATA_ISNULL) before producing a result; the interpreter (execExprInterp.c:935,962,986,1010) does the same. The inlined path contains no such store, so fcinfo->isnull retains any stale value from a prior evaluation of the reusable FunctionCallInfoData.

Impact: Latent invariant violation. The op *result* (resvalue/resnull) is correct for the allowlisted operators and no existing downstream consumer reads fcinfo->isnull for these operators today, so there is no live bug. A future aggregate transition, ScalarArrayOp, or caller inspecting fcinfo->isnull after evaluation would observe stale state.

Repair (verified, compiled): Store l_sbool_const(0) into the isnull field of the fcinfo once before the operator dispatch via l_struct_gep(b, StructFunctionCallInfoData, v_fcinfo, FIELDNO_FUNCTIONCALLINFODATA_ISNULL, ...). Part of the combined refactor patch (repair_combined.diff, sha256 904c6fabb5b9b142614fdcd0ebfc407f1f4e748def3a956023dcb9e86a9e1370; validated: apply-check=0, compile COMPILE_EXIT=0 no warnings).

F2

— MAJOR — correctness/robustness — src/backend/jit/llvm/llvmjit_expr.c:79-167

Missing strictness/property guard; inlined path hardcodes resnull=false relying on an implicit strictness invariant.

The inlined path stores resnull=false without consulting argument nullness, relying entirely on the strict EEOP_FUNCEXPR_STRICT_* opcode having already null-checked all args and reached b_nonull. This is safe *only because* the executor emits EEOP_FUNCEXPR_STRICT_2 for these strict 2-arg functions (execExpr.c:2782). The matcher selects by raw C pointer fn_addr == &int4eq and does not validate the semantic guarantees (strict, leakproof, 2 args, byval, returns bool) that make the inlining legal; there is no assertion/guard bounding the allowlist against drift. A copy-paste extension adding a non-strict or non-byval function would silently miscompile.

Impact: No incorrect result with the current catalog set and current opcode selection. Latent footgun for maintainers; RLS-adjacent worst case if the invariant were ever violated.

Repair (verified, compiled): (a) Gate the inlining call at the call site (~line 838) on the opcode being one of EEOP_FUNCEXPR_STRICT/STRICT_1/STRICT_2 (structural fix), making the safety property explicit; (b) add a header doc comment above llvm_try_inline_function_call enumerating the required properties. Part of the combined refactor patch (same sha256 as F1; validated: compile COMPILE_EXIT=0).

F3

Security

No memory-safety, privilege-escalation, SQL-injection, or authorization-bypass vulnerabilities found. The emitted LLVM IR is type-consistent and in-bounds (l_funcvaluep GEPs to the n'th NullableDatum slot; all operators have nargs==2; loads/stores match Datum/TypeStorageBool widths). The fn_addr pointer is read once at JIT-compile time and is immutable (no TOCTOU). The one security-adjacent concern (F2 / SEC-1) — unconditional resnull=false relying on strictness — is not currently exploitable because the executor never emits the non-strict EEOP_FUNCEXPR opcode for these strict operators; it is a latent footgun hardened by the F2 call-site guard.

Test-Gap Section

The new inlined path is reached only when JIT compiles the expression (jit=on + cost above threshold). The standard regression suite does not force JIT (jit=off in explain.sql; jit_above_cost default 100000), so the inlined operators' results are effectively untested. The proposed TAP test (F3) closes this gap by comparing jit=on vs jit=off over edge values and NULLs. A mutation-differential (swap LLVMIntEQ→LLVMIntNE and confirm int4eq parity fails) is recommended to prove the net covers the inlined path.
