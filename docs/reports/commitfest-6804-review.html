CommitFest 6804 Review: log_postmaster_stats

Summary

This patch introduces a new GUC log_postmaster_stats that causes the postmaster to periodically emit a LOG-level message summarizing recent connection, disconnection, and parallel-worker registration rates, along with postmaster process CPU usage (via getrusage(RUSAGE_SELF)). The feature is modeled after log_startup_progress_interval and is off by default (0 disables). It is SIGHUP-settable with a range of 0-86400 seconds and GUC_UNIT_S so the stored value is always in seconds.

The patch modifies ServerLoop to track running connection/disconnection counts and emit periodic stats, DetermineSleepTime to cap the idle wait at the stats interval, CleanupBackend to count external-connection exits, and adds GetParallelWorkerRegisterCount() to read the parallel worker registration counter for stats purposes.

Verdict: ready-for-committer

No BLOCKER or MAJOR findings. Two MINOR findings (one docs, one tests) were verified with concrete repair patches. The patch is mechanically sound, follows existing PostgreSQL patterns (e.g., pg_rusage_show usage in vacuum/recovery), and includes a TAP test. The deterministic verdict is ready-for-committer because no surviving findings are BLOCKER/MAJOR correctness or security issues.

Findings

PM-1

(MINOR, docs) — Documentation sample output split across two lines

Location: doc/src/sgml/config.sgml:8497

Mechanism: The <screen> block shows the sample log message split across two indented lines, implying the CPU: portion is a separate output line. However, the ereport() call in ServerLoop uses a single errmsg() with pg_rusage_show() result appended via %s, producing one continuous log line.

Failure: Users reading the documentation may expect two separate log lines when the server actually emits a single line containing both the rates and the CPU usage portion.

Verification: verified by static-check — the ereport at postmaster.c:1871 uses errmsg("postmaster stats: ...; %s", ..., pg_rusage_show(&pmstats_ru0)), producing a single-line message. The doc <screen> at config.sgml:8497-8498 splits it across two lines.

Repair: Merge the two-line sample into a single line. Repair patch validated: git apply --check passes, ninja docs succeeds.

PM-2

(MINOR, tests) — TAP test only checks connection rate field

Location: src/test/postmaster/t/005_log_postmaster_stats.pl:22

Mechanism: The wait_for_log regex only checks for avg .* conns/sec and does not verify the disconnection rate, parallel worker rate, or CPU usage portion of the LOG message.

Failure: A regression breaking disconnection counting, parallel worker rate, or CPU reporting could go undetected.

Verification: verified by static-check — the test regex at line 22 matches only the first field of the multi-field ereport output.

Repair: Replace with a comprehensive regex matching all fields including CPU usage. Repair patch validated: git apply --check passes, the improved TAP test passes (ok 1 - postmaster stats line emitted with all rate fields and CPU usage).

Security Review

No security concerns identified. The patch:

  • Uses getrusage(RUSAGE_SELF) which is process-local and does not

expose child process resource usage.

  • Uses unlocked read of parallel_register_count for stats purposes,

consistent with existing code patterns (the counter is uint32 and wrap-around arithmetic is acceptable for stats).

  • Does not introduce any new SQL-reachable attack surface.
  • Connection/disconnection counters are uint64 static variables

incremented only in the single-threaded postmaster ServerLoop.
