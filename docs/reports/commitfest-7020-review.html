The patch

diff
diff --git a/src/backend/storage/file/buffile.c b/src/backend/storage/file/buffile.c
--- a/src/backend/storage/file/buffile.c
+++ b/src/backend/storage/file/buffile.c
@@ -414,8 +414,9 @@ BufFileClose(BufFile *file)
 {
 	int			i;

-	/* flush any unwritten data */
-	BufFileFlush(file);
+	/* flush any unwritten data if it will not be deleted on close */
+	if (file->fileset != NULL)
+		BufFileFlush(file);
 	/* close and delete the underlying file(s) */
 	for (i = 0; i < file->numFiles; i++)
 		FileClose(file->files[i]);

The patch gates BufFileFlush in BufFileClose on file->fileset != NULL. Regular temp files (BufFileCreateTemp, fileset == NULL) are created with FD_DELETE_AT_CLOSE and unlinked by FileClose, so flushing their final dirty buffer before unlink is wasted I/O. FileSet-backed BufFiles (BufFileCreateFileSet/BufFileOpenFileSet, fileset != NULL) persist after close and may be re-opened by name; the patch preserves their flush.

Findings

[MINOR] PR-1 — src/backend/storage/file/buffile.c:417 — temp I/O statistics undercount

What: With the patch, the final BufFileFlush of a BufFileCreateTemp-based BufFile is skipped, so BufFileDumpBuffer (buffile.c:497) is not called for the closing dirty buffer. That function increments pgBufferUsage.temp_blks_written (buffile.c:578) and accumulates pgBufferUsage.temp_blk_write_time (buffile.c:572). After this patch, those counters no longer include the final write of a doomed temp file.

Why: EXPLAIN (BUFFERS) and pg_stat_statements temp_blks_written/temp_blk_write_time will report marginally lower I/O for queries that spill to disk (hashjoin batches, tuplestore overflow, GiST buffered build, backup manifest, serial sort). The effect is at most one BLCKSZ write per BufFile closed with a dirty buffer. Arguably the new numbers are more accurate — the skipped write was wasted I/O on a file about to be unlink()'d — but it is an observable behavioral change in instrumentation.

Verification: verified by inspection. BufFileFlush (buffile.c:724-731) calls BufFileDumpBuffer only when dirty; BufFileDumpBuffer (buffile.c:497-585, lines 553-557 and 562/578) performs the write and counter increments. The patch's if (file->fileset != NULL) gate (line 418) skips this for fileset == NULL temp files.

Repair (suggested): No code change required for correctness. The suggested repair is a comment expansion documenting the intentional stats undercount (combined with PR-2's comment fix). A concrete HEAD-bound unified diff was validated in disposable scratch: apply-check OK, diff-check OK, compile of buffile.o OK with zero warnings.

Suggested code (exact-postimage excerpt):

c
/*
 * Flush any unwritten data, but only for fileset-backed BufFiles whose
 * underlying physical files survive FileClose().  Plain temp files
 * (fileset == NULL) are created with FD_DELETE_AT_CLOSE, so FileClose()
 * unlinks them regardless of whether the final buffer is written;
 * skipping the flush therefore avoids a pointless write to a doomed
 * file.  As a consequence, pgBufferUsage.temp_blks_written and
 * temp_blk_write_time no longer account for that final write of a
 * doomed temp file; this is intentional.
 */
if (file->fileset != NULL)
    BufFileFlush(file);

Test example: waived (not-instrumentable) — comment-only change with no behavioral delta; a regression test cannot distinguish a comment change. The stats delta is documented in the comment rather than enforced by test.

[NIT] PR-2 — src/backend/storage/file/buffile.c:417 — comment wording imprecise

What: The comment says "flush any unwritten data if it will not be deleted on close" but the code predicate is file->fileset != NULL, which is a proxy for "the underlying physical files will not be deleted on close" (because FileSet-based files are created without FD_DELETE_AT_CLOSE, while OpenTemporaryFile sets it). The equivalence holds today but is an implicit invariant.

Why: A future reader or a future code path that creates a BufFile with fileset != NULL but FD_DELETE_AT_CLOSE set (or vice versa) would make the comment misleading.

Verification: verified by inspection. OpenTemporaryFile (fd.c:1754) sets FD_DELETE_AT_CLOSE; PathNameCreateTemporaryFile (fd.c:1872) sets only FD_TEMP_FILE_LIMIT (no FD_DELETE_AT_CLOSE); FileClose (fd.c:2022) unlinks only when FD_DELETE_AT_CLOSE is set.

Repair (suggested): Comment rewording making the fileset predicate and FD_DELETE_AT_CLOSE invariant explicit. Subsumed by the combined repair patch for PR-1.

Test example: waived (not-instrumentable) — comment-only style change with no behavioral delta.
