CommitFest 6557 — PL/pgSQL FOREACH ... IN JSON ARRAY — Review Report

Source: postgresql-master Slug: commitfest-6557-review Scope identity: pg-cf6557-head-2fb8da5a245661287833b05a1b2e275ddf83bbd7-staged-f717b158 Target: uncommitted staged diff against HEAD 2fb8da5a245661287833b05a1b2e275ddf83bbd7 Date reviewed: 2026-08-30 Verdict: waiting-on-author (2 verified BLOCKERs)

Summary

Adds FOREACH <target> IN JSON ARRAY <expr> LOOP ... END LOOP to PL/pgSQL: iterate JSON/JSONB array elements and assign each to a scalar, composite, or list-of-scalars loop variable. New statement type PLPGSQL_STMT_FOREACH_JSON_A, unreserved keyword JSON, executor exec_stmt_foreach_json_a, helper JsonbValueToDatum, an extended plpgsql_exec_get_datum_type_info (new refname out-param and a new PLPGSQL_DTYPE_ROW lazy tupdesc build), and a new regression test plpgsql_foreach.

The architecture (shared base struct + grammar refactor via foreach_type, JsonbIteratorNext with skipNested, json_populate_type for composite population) is reasonable. However, the staged patch has two verified BLOCKERs that crash the server or corrupt the heap, one verified MAJOR correctness defect (FOUND), and significant test-coverage gaps. The patch's own regression test crashes the backend (SIGABRT) on the list-of-scalars and record-field cases — the committed expected output does not match actual behaviour. Not ready for committer as-is.

Findings

BLOCKER F1 — Server crash: missing TupleDescFinalize before BlessTupleDesc

  • Class: correctness
  • Location: src/pl/plpgsql/src/pl_exec.c:5894 (plpgsql_exec_get_datum_type_info, new PLPGSQL_DTYPE_ROW branch)
  • Status: verified (by repro)
  • Mechanism: The new branch builds row->rowtupdesc via

CreateTemplateTupleDesc + TupleDescInitEntry/Collation and then calls BlessTupleDesc without first calling TupleDescFinalize. CreateTemplateTupleDesc initializes firstNonCachedOffsetAttr = -1 and relies on the caller to run TupleDescFinalize after populating entries; BlessTupleDesc asserts firstNonCachedOffsetAttr >= 0 (execTuples.c:2358). The missing TupleDescFinalize trips that assertion.

  • Failure: make installcheck against a --enable-cassert --enable-debug

build aborts the backend at the foreach x, y, z in json array case and the foreach c.x, c.y, c.z case with TRAP: failed Assert("tupdesc->firstNonCachedOffsetAttr >= 0") at execTuples.c:2358. The committed expected/plpgsql_foreach.out claims those cases succeed.

  • Repair: Build row->rowtupdesc in estate->func->fn_cxt (long-lived

compile context) and call TupleDescFinalize(row->rowtupdesc) before BlessTupleDesc. Concrete unified diff provided (bound to HEAD); validated: after applying, make installcheck reports all 14 plpgsql tests pass.

BLOCKER F2 — Use-after-free of row->rowtupdesc across cached function calls

  • Class: security (CWE-416)
  • Location: src/pl/plpgsql/src/pl_exec.c:5894
  • Status: verified (by repro)
  • Mechanism: Same branch builds row->rowtupdesc in the caller's

CurrentMemoryContext, which (from exec_stmt_foreach_json_a) is the transient stmt_mcontext. PLpgSQL_row datums of DTYPE_ROW are NOT copied per execution (copy_plpgsql_datums uses outdatum = indatum), so the executor's row datum IS the cached function's datum. After the loop, MemoryContextReset(stmt_mcontext) frees the TupleDesc but row->rowtupdesc is not reset to NULL; on the next cached invocation the if (!row->rowtupdesc) guard is false (dangling non-NULL pointer) and the freed TupleDesc is dereferenced. Reachable by any role with CREATE/EXECUTE on a function using a multi-scalar FOREACH JSON ARRAY.

  • Failure: A cached PL/pgSQL function with `FOREACH a, b, c IN JSON

ARRAY ... corrupts the heap on the second invocation. The regression tests only use DO` blocks (anonymous, not cached), so the second invocation is never exercised.

  • Repair: Same edit as F1 (build the tupdesc in estate->func->fn_cxt).

Validated: a persistent cached function called three times in succession returned without crash after the repair.

MAJOR F3 — FOUND is never set to true after the JSON loop

  • Class: correctness
  • Location: src/pl/plpgsql/src/pl_exec.c:3147
  • Status: verified (already raised on thread by Jim Jones, 2026-03-03)
  • Mechanism: exec_stmt_foreach_json_a declares bool found = false; and

never sets it true inside the WJB_ELEM branch; exec_set_found(estate, found) therefore always sets FOUND=false. Contradicts exec_stmt_foreach_a.

  • Repair: Add found = true; inside the if (r == WJB_ELEM) block.

Validated: non-empty → FOUND=true, empty → FOUND=false after the one-line fix.

Residual risk

The deeper composite-population reliability issue (the list-of-scalars field-by-name assignment produces NULLs under -O0/cached-function conditions while the DO-block -O2 path populates correctly) was observed during verification and is tied to the json_populate_type cache / rowtupdesc interaction; it is not raised as a separate finding here but warrants investigation once F1/F2 are fixed. The unresolved Tom Lane SubscriptRoutines design objection is a separate committer-level architectural concern.
