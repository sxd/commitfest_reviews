CommitFest 7656 — Review Report (v2)

Subject: amcheck: detect duplicate PostingItem keys in GIN posting trees Author: Stepan Neretin (slpmcf@gmail.com) — pgsql-hackers thread 651742 Verdict: ready-for-committer Blocker split: 0 verified / 0 unverified

Change summary

A single-line semantic change in contrib/amcheck/verify_gin.c, function gin_check_posting_tree_parent_keys_consistency: the ordering invariant check for adjacent PostingItem separator keys on GIN posting-tree internal pages is widened from ItemPointerCompare(...) < 0 to <= 0, so that equal (duplicate) adjacent separator keys are now also reported as ERRCODE_INDEX_CORRUPTED ("wrong tuple order in posting tree, block %u, offset %u"). The error message, errcode, and surrounding control flow are unchanged. A new TAP sub-test equal_posting_tree_internal_keys_test in contrib/amcheck/t/006_verify_gin.pl builds a 30000-row single-key GIN index, corrupts block 2 (posting-tree root) so the first PostingItem.key equals the second, and asserts the exact error.

Changed files: contrib/amcheck/verify_gin.c, contrib/amcheck/t/006_verify_gin.pl Changed symbol: gin_check_posting_tree_parent_keys_consistency

Correctness analysis

Rejecting equal adjacent separator keys is correct. In a GIN posting tree, an internal data page stores PostingItems whose .key is the separator TID that is the lower bound of the right child's TID range (built from real heap TIDs via dataPrepareDownlink). For per-child ranges to be disjoint and totally ordered, adjacent separators must be strictly increasing. GIN's insert/split paths never produce equal adjacent separators (heap TIDs are unique), so <= 0 cannot fire on any valid index — it converts a silent-pass corruption class into a reported one. The previous < 0 check silently accepted duplicate separators.

Rightmost (0,0) sentinel: not affected. The (0,0) rightmost item is validated by the separate if (i == maxoff && rightlink == InvalidBlockNumber) branch (verify_gin.c:317-332); the <= 0 ordering check lives in the else if (i != FirstOffsetNumber) branch, which is never taken for the rightmost sentinel. No false-positive risk.

Security analysis

No security issues. gin_index_check(regclass) is reachable only by superusers (REVOKE ALL ON FUNCTION ... FROM PUBLIC in amcheck--1.4--1.5.sql:14 and trusted = false in amcheck.control). The existing SECURITY_RESTRICTED_OPERATION + RestrictSearchPath() hardening in amcheck_lock_relation_and_check is untouched. No privilege escalation, TOCTOU, injection, crypto, or memory-safety surface is altered. The widened check cannot introduce false positives against valid GIN indexes (GIN never emits equal adjacent separators), and amcheck is report-only (no auto-REINDEX), so even a hypothetical false positive requires a separate admin decision.
