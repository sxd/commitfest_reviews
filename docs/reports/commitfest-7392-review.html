CommitFest 7392 Review: amorderbyvalsexact — ORDER BY values from index scan to targetlist

Summary

This patch adds a new amorderbyvalsexact flag to IndexAmRoutine that lets an ordering index scan (GiST, SP-GiST) hand the AM's ORDER BY distance values directly to the query's target list, instead of re-evaluating the ORDER BY expression on the heap tuple. This is a performance optimization for AMs whose reported distance values are exact (not approximate), and a correctness fix for AMs (like BM25 extensions) where re-evaluating the operator would produce different values than what the index reported.

The patch modifies the planner (setrefs.c, createplan.c, plancat.c) to rewrite targetlist entries matching ORDER BY expressions into INNER_VAR references to a virtual slot filled by the executor, the executor (nodeIndexscan.c) to populate that slot with the AM's values, EXPLAIN and ruleutils.c to deparse the new Vars correctly, and adds comprehensive regression tests in gist.sql.

Review Analysis

Design

The patch introduces a new amorderbyvalsexact boolean on IndexAmRoutine, propagated through IndexOptInfo and IndexScan plan nodes. When set, the planner's setrefs.c replaces targetlist expressions that are equal() to ORDER BY expressions with Var(INNER_VAR, i+1) references. The executor fills a virtual slot (iss_OrderBySlot) with the AM's ORDER BY values and installs it as the projection's inner tuple.

This mirrors the existing INDEX_VAR mechanism for Index Only Scan, which is the correct design precedent. The use of INNER_VAR for a scan node with no inner plan is safe because INNER_VAR is otherwise unused for scan nodes.

Correctness

  • The equal() match in replace_orderby_tlist_refs correctly identifies

targetlist entries that are the same expression as an ORDER BY key. Only top-level expressions are matched (not subexpressions), which is conservative and correct.

  • The type restriction to FLOAT8OID and FLOAT4OID is correct: those are the

only types index_store_float8_orderby_distances() can deliver.

  • The IndexRecheck modification correctly recomputes ORDER BY values from the

heap tuple during EPQ, ensuring the displayed values match the operator's computation rather than stale index values.

  • The reorder-queue path in IndexNextWithReorder correctly stores the queue

entry's ORDER BY values before the pop frees them.

Security

No security issues identified. The patch does not introduce any new privilege-escalation paths, search-path vulnerabilities, or memory-safety concerns. The virtual slot is properly allocated and managed within the executor's tuple table.

Test Coverage

The patch includes comprehensive regression tests in gist.sql that verify:

  • The counting-function test proves the operator is not re-evaluated

(sequence counter stays at zero).

  • The lossy box opclass test exercises the recheck and reorder-queue paths.
  • The FOR UPDATE test exercises row locking with ORDER BY value display.
  • EXPLAIN output shows the "Order By Values Used" property.

The only gap is the EPQ recheck path (COV-1), which requires an isolation test.
