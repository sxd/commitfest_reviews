CommitFest 7244 Review — effective_cpu_cache_size

Summary

The patch introduces a new planner cost GUC effective_cpu_cache_size (type int,

MAX_KILOBYTES). When aggstrategy == AGG_HASHED || AGG_MIXED and the GUC is > 0, cost_agg computes the hash-table resident size and charges an extra cpu_tuple_cost * HASH_RESIDENCY_PENALTY * LOG2(table_bytes / cache_bytes) * input_tuples when the table exceeds the configured cache size. HASH_RESIDENCY_PENALTY = 4.0.

The core idea is reasonable and the plumbing is clean (reuses hash_agg_entry_size/hash_agg_set_limits from nodeAgg.c, GUC in the cost-tuning group next to effective_cache_size). However, the patch should not be committed until the stale AGG_SORTED == AGG_HASHED invariant comment is reconciled and the new behavior is demonstrated with tests.

Verdict: waiting-on-author — 1 verified BLOCKER (stale comment + plan-instability risk), 1 verified MAJOR (no tests). 2 findings refuted (AGG_MIXED double-charge, LOG2 Inf).

Findings

PATCH-1

— BLOCKER (correctness/maintainability) — verified

Location: src/backend/optimizer/path/costsize.c:2874

The cost_agg block comment still states *"AGG_SORTED and AGG_HASHED have exactly the same total CPU cost"* and instructs maintainers to *"form the same intermediate values in the same order"*. The patch adds hash_entry_cost (nonzero only for AGG_HASHED/AGG_MIXED) to both strategy branches, breaking the asserted equality. While the patch added an explanatory paragraph at costsize.c:2870-2872, it left the contradicting invariant sentence standing.

Evidence (executed): Live EXPLAIN on the feature build confirmed AGG_HASHED total cost rises from 17900.50 (at effective_cpu_cache_size=8MB, table fits) to 121844.01 (at 1kB, penalty applies). AGG_SORTED total is unaffected by the GUC. The cost delta is exactly hash_entry_cost.

Repair (passed validation): Update the stale comment to state the totals are equal only when hash_entry_cost is zero, documenting the penalty as intentional plan-steering behavior. Comment-only fix; compiled and validated alongside PATCH-2's test. Patch SHA-256: a23ca1efe2c6db7c53810e6c93c6c27d370f8b301d29511c6c750c0a7b0fc855.

PATCH-3

— MAJOR (correctness) — refuted

Location: src/backend/optimizer/path/costsize.c:2829

Claim: AGG_MIXED charges the full input_tuples penalty, then each hashed sub-rollup is separately costed as AGG_HASHED with the same subpath->rows, double-charging for grouping sets.

Refutation: The per-rollup full-input_tuples charge pattern is identical to the pre-existing, long-standing hash-agg spill disk/CPU cost treatment (costsize.c:2966-3025: spill_cost = depth * input_tuples * 2.0 * cpu_tuple_cost). The "don't charge input cost again" comment at pathnode.c:3250-3251 refers to input_startup_cost/input_total_cost (passed as 0.0, 0.0), not per-tuple hash-probe work. The patch introduces no new inconsistency.

SEC-1

— MAJOR (security) — refuted

Location: src/backend/optimizer/path/costsize.c:2853

Claim: LOG2 can produce Inf because entrysize * numGroups can overflow to +Inf.

Refutation: numGroups is clamped by clamp_row_est to MAXIMUM_ROWCOUNT=1e100. entrysize is a finite Size (max ~1.8e19 on 64-bit). The product cannot reach DBL_MAX (~1.8e308). LOG2 input is guarded by table_bytes > cache_bytes with cache_bytes > 0, so the argument is finite and > 1. No Inf, NaN, or division by zero is reachable. Matches existing LOG2 convention at costsize.c:2008 and :506.

Security Review
