CommitFest 7577 — Stale hash entries when reusing an auxiliary resource owner

Patch summary

The patch fixes a reuse bug in ReleaseAuxProcessResources() introduced by b8bff07daa8. After sorting and bulk release, stale copies of hash entries remain beyond the sorted prefix, but the function only resets the counts and flags (releasing, sorted) before marking the auxiliary owner reusable. On reuse, stale slots can be mistaken for freshly acquired resources (causing double release) or leave the table with no empty slots, making ResourceOwnerAddToHash() probe indefinitely (hang).

Fix (implementation): src/backend/utils/resowner/resowner.c

c
	if (AuxProcessResourceOwner->hash != NULL)
		memset(AuxProcessResourceOwner->hash, 0,
			   AuxProcessResourceOwner->capacity * sizeof(ResourceElem));

Tests: adds test_resowner_aux(int4) to test_resowner exercising reuse across the array-only and hash-table regimes (16, 64, 65, 1024 resources) for two rounds, asserting each resource is released exactly once. v2 of the test fails promptly (duplicate-release count error) with the fix reverted rather than hanging.

The implementation change is correct and self-contained: the guard hash != NULL handles the array-only fast path; capacity * sizeof(ResourceElem) matches the MemoryContextAllocZero allocation; and the fixed-size arr needs no clearing because array lookups are bounded by narr.
