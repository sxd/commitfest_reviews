CommitFest 6842 Review: Prevent constraint name conflicts in partition trees spanning multiple schemas

Author: Marko Grujic Bug: #19507 Verdict: ready-for-committer Blockers: 0 verified, 0 unverified

Scope

ChooseConstraintName picks a constraint name unique within a given relation's namespace. When invoked for a partition root, the chosen name is not guaranteed to be unique for any partition in a different schema. This patch introduces ChooseConstraintNameForRelation(Oid relid, ...), which wraps ChooseConstraintName but also excludes all pre-existing constraints across the entire partition hierarchy. When the relation has no descendants, behavior is identical to ChooseConstraintName.

Findings

F1

— NIT/maintainability: Incomplete conversion of AddRelationNotNullConstraints auto-name call sites (verified)

Location: src/backend/catalog/heap.c:3091, src/backend/catalog/heap.c:3169

AddRelationNotNullConstraints (the CREATE TABLE / inherited NN path) still calls ChooseConstraintName directly. The patch converted the sibling sites in AddRelationNewConstraints and ATExecSetNotNull but left these two. The CREATE TABLE path is currently immune (fresh relation has no pre-existing descendant constraints), but the asymmetry is a maintenance hazard.

Repair: Convert both sites to ChooseConstraintNameForRelation. Patch SHA-256: c2c697e0208e6cc0aea6c4e6cc443b64f8f03b2b00d26762bc495c6d0b46858d. Validation: passed (apply-check, compile, targeted-test).

F4

— NIT/correctness: find_all_inheritors NoLock race window (refuted)

Location: src/backend/catalog/pg_constraint.c:621

find_all_inheritors with NoLock is the established read-only enumeration pattern (vacuum.c:1014, lockcmds.c:134, indexcmds.c:1367). Both failure modes (concurrently-dropped child → stale over-constraining; concurrently-added child → no pre-existing constraints) are harmless. No worse than the pre-existing ChooseConstraintName TOCTOU documented in its header comment. Refuted — no actionable defect.

F5

— NIT/maintainability: get_rel_name NULL defensive guard (verified)

Location: src/backend/catalog/pg_constraint.c:614

get_rel_name returns NULL if the relation was concurrently dropped. The lock invariant holds at all call sites so the root cannot be dropped underneath, but an explicit guard makes the invariant self-documenting. Patch SHA-256: cb100770d3973c441850da80a3f82cd887c46dcf86558196517c7aec614e6284. Validation: passed (apply-check, compile, targeted-test). Test waived (not-instrumentable: guarded branch unreachable under lock invariant).

Security Review

No BLOCKER/MAJOR/MINOR security findings. The patch adds a catalog name-picking helper with no new SQL-reachable surface, no privileged operation, no SECURITY DEFINER, no string-SQL assembly, and no authz bypass. The TOCTOU window it introduces is the same class and actor class as the pre-existing ChooseConstraintName race, and the root is held under a self-conflicting lock for the whole transaction. Authz is unchanged: only the partitioned-root owner can reach the new code. Security verdict: ship-from-security-perspective.
