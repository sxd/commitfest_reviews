CommitFest 7371 — Review Report: Fix missing tts_tid in ExecForceStoreHeapTuple

Summary

Verdict: waiting-on-author (1 verified BLOCKER: test gap)

The patch adds slot->tts_tid = tuple->t_self; in the TTS_IS_BUFFERTUPLE branch of ExecForceStoreHeapTuple (src/backend/executor/execTuples.c:1768). This is a correct, minimal, one-line bug fix that restores the slot's tts_tid invariant after ExecClearTuple invalidated it, matching the established convention of tts_heap_store_tuple (line 497) and tts_buffer_heap_store_tuple (line 962).

The bug

KNN GiST scans with lossy distance recheck use a reorder queue in nodeIndexscan.c. When popping a tuple from the queue, ExecForceStoreHeapTuple is called with a buffer tuple slot. The TTS_IS_BUFFERTUPLE branch copies the tuple via heap_copytuple but previously did not set slot->tts_tid from tuple->t_self, leaving it at the InvalidItemPointer (4294967295,0) set by ExecClearTuple. With FOR UPDATE, the invalid tid is passed to heap_lock_tuple, which extends the relation with an orphan block before aborting with "attempted to lock invisible tuple".

Findings

F-1

— BLOCKER — tests — Regression test does not exercise the buggy reorder-queue pop path

Location: src/test/regress/sql/gist.sql:246-251

Mechanism: The staged test queries ORDER BY v <-> point(50, 50) LIMIT 1 over circles centered at (i,i) with radius 0.5. For circle id=50, the query point (50,50) is inside the bounding box, so bbox distance = 0 and true distance = 0, making was_exact = true. With LIMIT 1 and an empty queue, the tuple is returned immediately without ever calling reorderqueue_push/reorderqueue_pop. The buggy ExecForceStoreHeapTuple pop path at nodeIndexscan.c:257 is NOT exercised.

Failure: A future regression reintroducing the missing tts_tid would not be caught. The test passes with or without the fix.

Verification: verified by static analysis and two-run validation. A replacement test was designed (querying point(0,0) outside all bounding boxes, forcing 100 reorder-queue pops) and validated: PASS on HEAD (with fix, all ctids valid), FAIL on BASE (without fix, all ctids = (4294967295,0), ERROR: attempted to lock invisible tuple).

Repair: Replace the weak test block with the strong test. The repair patch (f1-strong-test.patch) was applied, built, and pg_regress gist passed.

F-2

— MINOR — correctness — tts_tableOid not set in BUFFERTUPLE branch (pre-existing)

Location: src/backend/executor/execTuples.c:1759-1774

Mechanism: The TTS_IS_BUFFERTUPLE branch of ExecForceStoreHeapTuple does not set slot->tts_tableOid, unlike ExecStoreHeapTuple (line 1649) and ExecStoreBufferHeapTuple (line 1690) which both set slot->tts_tableOid = tuple->t_tableOid. Pre-existing, surfaced by this patch.

Verification: verified by static source comparison across sibling functions.

Repair: Add slot->tts_tableOid = tuple->t_tableOid; in the same branch.

F-3

— NIT — maintainability — No comment explaining why tts_tid must be set

Location: src/backend/executor/execTuples.c:1768

Mechanism: The patched line has no comment. ExecClearTuple invalidated tts_tid, and slot_getsysattr reads ctid from slot->tts_tid (not from the copied tuple). A future refactor might remove the line as "redundant".

Verification: verified by static analysis.

Repair: Add a two-line comment explaining the invariant restoration.
